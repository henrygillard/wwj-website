# Phase 03: Code Review Report

**Reviewed:** 2026-05-18
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

This phase adds WebP image conversion, intrinsic dimension data in `photos.js`, preload/lazy-load plumbing across components, and `preload="none"` on videos. The CWV-oriented changes in the components and `index.html` are structurally sound. The critical defect is a workflow sequencing gap: `sync-and-deploy` (the only deploy path) overwrites `photos.js` and strips the `width`/`height` fields that `convert-images.mjs` adds, causing a guaranteed CLS regression every time content is synced to production. Two additional warnings cover a case-sensitivity bug in the conversion script and missing npm script bindings for the two new tools.

---

## Critical Issues

### CR-01: `sync-and-deploy` destroys `width`/`height` in `photos.js` on every content sync

**File:** `package.json:9` / `scripts/sync-from-sheet.mjs:165`

**Issue:** `sync-and-deploy` runs `sync-from-sheet.mjs`, which rebuilds `photos.js` with only `{ src, alt, group }` per entry — no `width` or `height`. It then commits and deploys. After any content sync, the deployed `photos.js` has no dimension fields. `Gallery.jsx` passes `photo.width` and `photo.height` directly as `<img>` attributes (line 36); both will be `undefined`. The CSS uses `height: auto` on the grid images. Without the intrinsic-size hint, the browser reserves zero height for each image until it loads, causing layout shifts (CLS) in the masonry column grid.

`convert-images.mjs` is a one-time offline tool: the source JPEGs are not committed, so it cannot be re-run in CI or on the server. The `width`/`height` fields it wrote were correct at conversion time but are erased on every subsequent `sync-and-deploy`.

**Fix:** Persist `width` and `height` separately from the mutable content data. Two viable approaches:

Option A — keep a static dimension registry that `sync-from-sheet` never touches:
```js
// src/data/photo-dimensions.js  (committed, never overwritten by sync)
export const PHOTO_DIMENSIONS = {
  'barton-springs/DSC06956.webp': { width: 800, height: 533 },
  // … one entry per image
}
```
Then in `Gallery.jsx`, merge at render time:
```jsx
import { PHOTO_DIMENSIONS } from '../data/photo-dimensions'
// …
const dims = PHOTO_DIMENSIONS[photo.src.replace('/photos/', '')] ?? {}
<img src={photo.src} alt={photo.alt}
     width={dims.width} height={dims.height} loading="lazy" />
```

Option B — have `sync-from-sheet.mjs` read the existing `photos.js`, merge existing `width`/`height` values into any matching entries, and only set them to `undefined` for truly new photos (triggering a clear CI warning).

## Warnings

### WR-01: `convert-images.mjs` writes a misleading header comment that triggers CR-01

**File:** `scripts/convert-images.mjs:132-133`

**Issue:** After converting and writing `photos.js`, the script emits this header into the file:

```
// Auto-generated — do not edit by hand.
// Run `npm run sync-content` to pull updates from Google Sheets.
```

Running `npm run sync-content` is exactly what erases the `width`/`height` fields the script just computed (see CR-01). Any developer who follows this instruction — or who sees the identical comment already in the committed `photos.js` (lines 1-2) — will inadvertently trigger the CLS regression.

**Fix:** Change the comment to accurately describe the two-step process:

```js
const photosJs =
  `// Auto-generated by scripts/convert-images.mjs — do not edit by hand.\n` +
  `// Width/height fields are required for CLS prevention.\n` +
  `// WARNING: running \`npm run sync-content\` will overwrite this file and strip\n` +
  `// width/height. If you re-sync, re-run \`node scripts/convert-images.mjs\` afterwards.\n\n` +
  `export const allPhotos = ${JSON.stringify(updatedPhotos, null, 2)}\n`
```

The same fix should be applied to the comment already present in the committed `src/data/photos.js:1-2`.

### WR-02: Uppercase `.JPG` extension breaks `convert-images.mjs` at the basename-strip step

**File:** `scripts/convert-images.mjs:84,88`

**Issue:** Line 84 filters files with `f.toLowerCase().endsWith('.jpg')`, which correctly matches both `.jpg` and `.JPG`. Line 88 then strips the extension with:

```js
const basename = path.basename(filename, '.jpg')
```

`path.basename` performs a literal suffix match (case-sensitive). A filename `DSC06956.JPG` passes the filter but produces basename `DSC06956.JPG` instead of `DSC06956`, which is then used as the key in `dimensionMap`. When `convert-images` later iterates `photos.js` entries and looks up `dimensionMap['DSC06956']`, it finds nothing and throws:

```
Error: No conversion result found for basename: DSC06956 (src: /photos/barton-springs/DSC06956.webp)
```

All current files happen to use lowercase `.jpg`, but this is a latent bug: adding a single photo from a camera that names files `.JPG` will crash the script silently mid-run.

**Fix:**
```js
// line 88 — strip extension case-insensitively
const basename = filename.replace(/\.(jpg|jpeg)$/i, '')
```

### WR-03: `convert-images.mjs` and `verify-images.mjs` are not reachable via any npm script

**File:** `package.json:6-13`

**Issue:** Neither `scripts/convert-images.mjs` nor `scripts/verify-images.mjs` is listed in `package.json`. Developers can only discover and run them by reading the file comments. `verify-images.mjs` in particular reads like a CI gate (exits 1 on failure) but has no hook to attach to `build` or a `precommit` step. Without an entry point, both tools are easily overlooked during onboarding and in CI pipelines.

**Fix:** Add npm script bindings:
```json
"scripts": {
  "convert-images": "node scripts/convert-images.mjs",
  "verify-images":  "node scripts/verify-images.mjs",
  "build": "npm run verify-images && vite build && vite build --config vite.config.ssr.js && node scripts/prerender.mjs"
}
```
Attaching `verify-images` as a `build` prerequisite ensures the CI build fails fast if a re-sync stripped image dimensions or a file is missing.

### IN-01: Hardcoded Google Sheets spreadsheet ID in `sync-from-sheet.mjs`

**File:** `scripts/sync-from-sheet.mjs:15`

**Issue:** `SPREADSHEET_ID = '1T0McDXR7VJ_Af1S8erm59_cqTGWvJoJ8_WYbjK0RoNk'` is committed in source. The `.env.example` documents the service-account credential but not the spreadsheet ID. If the sheet is ever migrated or the project is forked, there is no `.env` variable to update — developers must hunt for the hardcoded string.

**Fix:** Read from environment with a fallback error:
```js
const SPREADSHEET_ID = process.env.GOOGLE_SPREADSHEET_ID
if (!SPREADSHEET_ID) {
  console.error('Set GOOGLE_SPREADSHEET_ID in .env')
  process.exit(1)
}
```
And add to `.env.example`:
```
GOOGLE_SPREADSHEET_ID=1T0McDXR7VJ_Af1S8erm59_cqTGWvJoJ8_WYbjK0RoNk
```

### IN-02: `<video title>` attribute in `VideoSection.jsx` is non-standard

**File:** `src/components/VideoSection.jsx:15`

**Issue:** `title={recapVideo.title}` is passed to the `<video>` element. `title` is not a valid HTML attribute for `<video>` and has no effect on accessibility or SEO. Screen readers announce video controls but do not read the `title` attribute of a `<video>` element. If the intent is to label the video for assistive technology, `aria-label` should be used instead.

**Fix:**
```jsx
<video
  src={recapVideo.src}
  poster="/photos/barton-springs/hero-1.webp"
  aria-label={recapVideo.title}
  controls
  preload="none"
  className={styles.embed}
/>
```

### IN-03: `photos.js` has 32 entries but `verify-images.mjs` checks 35 files — cover-image and hero images are invisible to the data layer

**File:** `scripts/verify-images.mjs:20-59` / `src/data/photos.js`

**Issue:** `verify-images.mjs` correctly checks all 35 WebP files (including `hero-1.webp`, `hero-2.webp`, `cover-image.webp`). However, `photos.js` contains only 32 entries — the three non-gallery images are referenced in `About.jsx` (hardcoded constants, lines 4-5) and `About.module.css` (CSS background URL, line 5) but never appear in the data file. If a future `sync-from-sheet` run or a manual photo rename changes those paths, there is no data-layer record to update and the references in the component and CSS will silently serve a 404.

**Fix (low priority):** Add `hero-1`, `hero-2`, and `cover-image` to `photos.js` with a role marker (e.g., `"role": "hero"` or `"role": "cover"`) so a future automated check can cross-reference all referenced paths against the verified file list.
