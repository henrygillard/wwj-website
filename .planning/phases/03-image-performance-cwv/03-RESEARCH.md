## Summary

Phase 3 converts 35 JPEG images (totalling 139.3 MB on disk) to compressed WebP files, adds
explicit `width` and `height` attributes to every `<img>` element across the codebase, and
adds an LCP preload hint for the hero image in `index.html`. The images are currently raw
DSLR exports — barton-springs photos range from 4–10 MB each at 6000–10,000 px wide; they
need aggressive resizing as well as format conversion.

The conversion is a local build step. `sharp` (Node.js, v0.34.5) is the correct tool for this
project: it installs as an npm devDependency, works on Node 22 (confirmed compatible), and
requires no system-level binaries. `cwebp`, `sips` (tested and fails on this OS), and
ImageMagick are all absent — they cannot be used without additional setup. A single
`scripts/convert-images.mjs` script should handle all 35 images in one pass, producing
`.webp` replacements alongside the originals, then a cleanup step removes the originals.

`photos.js` is auto-generated by `sync-from-sheet.mjs` and carries a "do not edit by hand"
header. Because future syncs would overwrite any manual `.jpg → .webp` path edits, the sync
script must be patched to normalise photo src paths from `.jpg` to `.webp` on write. Hardcoded
paths in `About.jsx`, `Hero.jsx`, `VideoSection.jsx`, `About.module.css`, and `index.html`
must be updated individually.

**Primary recommendation:** Write `scripts/convert-images.mjs` using `sharp` as a devDependency;
have it resize and convert every file, emit output dimensions, and update `photos.js` in the
same pass. Then patch remaining hardcoded paths and add the preload hint.

### Pattern 1: sharp Batch Conversion Script

**What:** Node ESM script that walks the `public/photos/` directory, converts each JPEG to
WebP with resize, and emits output dimensions for use in the data file.

**When to use:** One-time migration. Also re-runnable if new photos are added later.

```javascript
// Source: https://github.com/lovell/sharp (Context7 /lovell/sharp)
import sharp from 'sharp'
import { readdir, unlink } from 'node:fs/promises'
import { resolve, extname, basename } from 'node:path'

async function convertImage(inputPath, outputPath, maxWidth) {
  const info = await sharp(inputPath)
    .resize(maxWidth, null, { fit: 'inside', withoutEnlargement: true })
    .webp({ quality: 75 })
    .toFile(outputPath)
  return { width: info.width, height: info.height }
}
```

`fit: 'inside'` with `withoutEnlargement: true` ensures portrait images scale correctly
and images smaller than `maxWidth` are not upscaled. [VERIFIED: Context7 /lovell/sharp]

### Pattern 2: Updating photos.js with Width/Height

**What:** After conversion, the script rewrites `src/data/photos.js` with `.webp` paths
and `width`/`height` fields per entry. Gallery.jsx then passes these as attributes.

```javascript
// photos.js entry format (after conversion):

```

### Pattern 3: LCP Preload Hint (index.html)

**What:** `<link rel="preload">` in `<head>` tells the browser to fetch the hero image at
high priority before it discovers it via the video element's `poster` attribute.

```html
<!-- Source: https://web.dev/articles/fetch-priority [CITED] -->
<!-- Add immediately after <link rel="canonical"> -->
<link rel="preload" as="image" href="/photos/barton-springs/hero-1.webp" fetchpriority="high" />
```

The `poster` attribute on a `<video>` element is a valid LCP candidate. When `preload="none"`
is set on the video (as it is here), the poster is what the browser shows first — making it
the primary LCP element. Preloading it with `fetchpriority="high"` is the correct pattern.
[VERIFIED: DebugBear / web.dev sources]

### Pattern 4: Updating sync-from-sheet.mjs to Preserve .webp Paths

**What:** Patch the photos data normalisation in `sync-from-sheet.mjs` so future syncs do
not revert photo src paths from `.webp` back to `.jpg`.

```javascript
// In sync-from-sheet.mjs, photos section — patch the path normalisation:
photoItems.push({
  src: row[0].replace(/\.jpg$/i, '.webp'),  // ← normalise extension
  alt: row[1] ?? '',
  group: row[2] ?? ''
})
```

This makes the sync script idempotent: whether the Sheet contains `.jpg` or `.webp` paths,
the generated `photos.js` always uses `.webp`.

### Anti-Patterns to Avoid

- **Relying on sips for WebP conversion:** sips does not support WebP output on this machine (tested). Do not use.
- **Using `<picture>` + `<source type="image/webp">` elements:** Adds complexity without benefit — all target browsers support WebP natively. The requirements ask for WebP files directly, not multi-format fallback.
- **Deleting .jpg files before verifying .webp output:** Convert first, verify file sizes, then delete originals. Do not delete in the same script pass.
- **Setting `loading="eager"` on gallery images:** Gallery images are below the fold — keep `loading="lazy"` to avoid blocking LCP.
- **Setting `loading="lazy"` on the hero image poster:** The preload hint handles early fetch; if an `<img>` were used for hero, it must NOT be lazy. (N/A here — hero uses `<video>` poster, not `<img>`.)
- **Writing width/height as CSS dimensions in attributes:** The `width`/`height` HTML attributes must reflect the image's intrinsic dimensions (post-resize), not the CSS display size. This is what allows the browser to compute aspect ratio before the image loads.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JPEG → WebP conversion | Custom binary wrapper / shell exec | `sharp` npm package | sharp handles colour profiles, EXIF, progressive JPEG edge cases; WebP encoder parameters are non-trivial |
| Image resize to specific width | Manual pixel math | `sharp().resize(maxWidth, null, { fit: 'inside' })` | `fit: 'inside'` handles portrait vs landscape correctly in one call |
| Batch dimension extraction | sips / exiftool | `sharp(path).metadata()` or capture from conversion output | Conversion output already includes final width/height — no second pass needed |

**Key insight:** WebP encoding quality curves are non-linear. A quality of 75 typically yields
4–8x smaller files than the source JPEG while preserving visual quality for photo content.
Do not hand-tune quality per image — batch q75 is the standard starting point.

## Common Pitfalls

### Pitfall 1: Hero image resize dimension — portrait vs width target
**What goes wrong:** hero-1.jpg is 4184×6276 (portrait). Resizing to `1920` wide produces
a 1920×2882 image — which is correct for full-viewport display. Using `{ fit: 'inside' }` is
essential so portrait images aren't cropped.
**Why it happens:** The default sharp fit is `'cover'`, which crops. `'inside'` preserves
aspect ratio without crop.
**How to avoid:** Always use `.resize(maxWidth, null, { fit: 'inside', withoutEnlargement: true })`.
**Warning signs:** Output image is square or has unexpected aspect ratio.

### Pitfall 2: photos.js auto-generation reverts .webp paths on next sync
**What goes wrong:** Running `npm run sync-content` overwrites `photos.js` with the paths
from Google Sheet (which still contain `.jpg`), undoing the conversion.
**Why it happens:** The sync script writes paths verbatim from the sheet.
**How to avoid:** Patch `sync-from-sheet.mjs` to normalise `.jpg → .webp` on the photoItems
push line. See Pattern 4 above.
**Warning signs:** After a content sync, gallery images 404.

### Pitfall 3: Width/height attributes must be intrinsic (post-resize) dimensions
**What goes wrong:** Setting CSS pixel values (e.g., `width="400"`) instead of the image's
actual pixel dimensions (e.g., `width="800"`). CLS prevention depends on the browser computing
the correct aspect ratio from intrinsic dimensions, not CSS layout dimensions.
**Why it happens:** Confusion between CSS display size and intrinsic image size.
**How to avoid:** Capture `info.width` and `info.height` from the sharp `.toFile()` return
value and embed those numbers in `photos.js`. For About/Nav, measure from the output file.
**Warning signs:** CLS score still non-zero despite attrs being present; images show at wrong
aspect ratio before CSS loads.

### Pitfall 4: Preload hint path must exactly match the served path
**What goes wrong:** Preload hint points to `hero-1.jpg` but actual path is now `hero-1.webp`.
Browser makes two requests (one wasted).
**Why it happens:** Updating the video poster but forgetting the preload link, or vice versa.
**How to avoid:** Update `index.html` preload href and video poster in the same edit.
**Warning signs:** Lighthouse flags "preload link is not used" or LCP is still slow.

### Pitfall 5: cover-image.jpg CSS reference — not auto-updated by script
**What goes wrong:** The conversion script processes all `.jpg` files in `public/photos/`
correctly, but `About.module.css` still references `cover-image.jpg` as a CSS background URL.
No `<img>` element exists for this image, so a component-level scan would miss it.
**Why it happens:** CSS background URLs are not co-located with the component JSX.
**How to avoid:** The update map above includes `About.module.css` — treat it as an explicit
step in the reference-update task.
**Warning signs:** About section background image 404s after `.jpg` files are removed.

### Pitfall 6: og:image and JSON-LD image must also be updated
**What goes wrong:** Social sharing and schema still point to `.jpg` path after deletion.
**Why it happens:** `index.html` has three hardcoded `hero-1.jpg` references (og:image,
twitter:image, MusicGroup JSON-LD image field). Easy to miss one.
**How to avoid:** Search `index.html` for `hero-1.jpg` before closing the task — confirm 0 remaining.

## Code Examples

### Full sharp WebP conversion with output dimensions
```javascript
// Source: Context7 /lovell/sharp — api-output.md, api-resize.md
import sharp from 'sharp'
import path from 'node:path'

async function convertToWebP(inputPath, maxWidth, quality = 75) {
  const dir = path.dirname(inputPath)
  const base = path.basename(inputPath, path.extname(inputPath))
  const outputPath = path.join(dir, `${base}.webp`)

  const info = await sharp(inputPath)
    .resize(maxWidth, null, { fit: 'inside', withoutEnlargement: true })
    .webp({ quality })
    .toFile(outputPath)

  return { outputPath, width: info.width, height: info.height, size: info.size }
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| JPEG for all web images | WebP as default web format | ~2020 (broad browser support) | 25–35% smaller than JPEG at same quality |
| `width`/`height` omitted (reflowed by CSS) | Explicit attrs + `aspect-ratio` CSS for CLS-0 | Chrome 79+ (2019) | Browser reserves space before image loads |
| `fetchpriority` absent | `fetchpriority="high"` on LCP preload | Chrome 101 (2022), Firefox 132 (Oct 2024) | 100–400ms LCP improvement |

**Deprecated/outdated:**
- JPEG for gallery/hero images: still functional but 2–4x larger than equivalent WebP
- Omitting `width`/`height` on `<img>`: causes CLS, Lighthouse penalises it
